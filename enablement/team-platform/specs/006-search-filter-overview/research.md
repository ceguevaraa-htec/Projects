# Phase 0 Research: Search, Filter & Employee Overview — Backend Gap Closure (EPIC-0006)

## Decision: `minAvailability` and `sort=utilization` — fetch-all-then-filter/sort in application code (Domain Logic), not SQL

**Question raised explicitly by the plan input**: since utilization isn't a stored column, does closing this gap mean fetching all employees and filtering/sorting in application code, or is there another approach?

**Decision**: Yes — fetch the full (already-SQL-filtered-by-`skill`/`proficiency`/`seniority`) employee result set from the repository exactly as today, then, in `EmployeeService` (Domain Logic, not the repository, not the route), compute each employee's current utilization via the existing `AssignmentService.getCurrentUtilization`, and apply `minAvailability` filtering and `sort=utilization` ordering over that in-memory, utilization-annotated list before returning it to the route.

**Rationale**:
- At demo scale (tens of employees, per the constitution's Principle V rationale and every prior epic's stated scale assumption), fetching the full filtered set and computing utilization per employee is O(n) extra work with n in the tens — the same cost profile `bench.service.ts` already accepts for every employee on every bench request, and no epic in this project has ever introduced pagination or a materialized/denormalized utilization column to avoid it.
- **Alternatives considered and rejected**:
  - *A materialized/cached utilization column on `employees`, updated on every assignment change* — rejected: this duplicates state that's already correctly derivable on read (exactly the kind of drift-prone denormalization SDP ADR-0005's centralization principle exists to avoid), and no other feature in this codebase needs it — `getCurrentUtilization` is called fresh, every time, everywhere else it's used (Employee detail, candidates, bench, self-service). Introducing the one cached exception here for query-performance reasons that don't actually exist at this scale isn't justified.
  - *Push utilization computation into SQL as a computed/correlated subquery inside `employee.repository.ts`* — rejected: this would mean re-deriving "current utilization" as raw SQL, duplicating the exact logic `AssignmentService.getCurrentUtilization` already owns (`includesToday` filtering + capacity sum) in a second place, which is precisely the duplication SDP NFR-0009/ADR-0005 forbid. The repository layer's contract in this codebase is "pure Kysely queries, no business logic" (see every repository file's own header comment) — a hand-written SQL reimplementation of utilization would break that contract worse than moving the filter/sort to Domain Logic does.
  - **Adopted — compute-then-filter/sort in Domain Logic**: keeps `getCurrentUtilization` as the single implementation (Principle II/NFR-0009 fully honored), keeps the repository free of business logic (its existing SQL-pushdown filters for `skill`/`proficiency`/`seniority` are untouched), and accepts the one narrow, explicitly-documented exception to "filtering/sorting happens in the repository" that a non-stored, Domain-Logic-derived value structurally requires. See plan.md's Constitution Check for the explicit Principle II call-out.

## Decision: one utilization-computation pass serves both `minAvailability` and `sort=utilization`

**Question raised explicitly by the plan input**: confirm this doesn't duplicate the utilization computation between the filter and the sort.

**Decision**: `EmployeeService.listEmployees` computes `currentUtilizationPercent` once per employee (via `Promise.all` over `AssignmentService.getCurrentUtilization` calls, mirroring the existing `Promise.all` pattern already used for `assignments`/`currentUtilizationPercent` composition in the route layer), producing an in-memory list of `{ employee, currentUtilizationPercent }` pairs. Both `minAvailability` filtering (`100 - currentUtilizationPercent >= minAvailability`) and `sort=utilization` ordering read from that same computed list — neither re-calls `getCurrentUtilization`.

**Rationale**: A single computation pass avoids the two-call-per-employee cost a naive "filter first, then separately re-fetch for sort" implementation would incur, and avoids two independent call sites that could silently drift if one were later changed without the other (the same anti-duplication reasoning as everywhere else in this codebase).

**Alternatives considered**: Compute utilization inside the filter step only, and separately inside the sort step only, applied as two independent passes — rejected: doubles the number of `getCurrentUtilization` calls for no benefit, and is exactly the kind of duplication this decision is written to rule out explicitly.

## Decision: `currentProjectNames` reuses the existing `AssignmentService.listEmployeeAssignments`, no new repository method

**Question raised explicitly by the plan input**: confirm which existing method is reused (`findAllForProject` vs. `findAllForEmployee`), or justify a new one.

**Decision**: Reuse `AssignmentService.listEmployeeAssignments(employeeId)` — the existing thin wrapper around `AssignmentRepository.findAllForEmployee` already used twice in `employees.routes.ts` (the `GET /:employeeId` and `PATCH /:employeeId` handlers). For each employee in the list response, call it, filter the returned `AssignmentRecord[]` to `temporalStatus === "current"` (already computed by the repository's `toRecord` mapping — confirmed via `src/repositories/assignment.repository.ts`'s `toRecord`, which sets `temporalStatus` from `isInFuture`/`includesToday` on every row, including `projectName` directly on each row already), map to `projectName`, and de-duplicate.

**Rationale**: `findAllForEmployee` is the correct access pattern here — this is a per-employee query ("what are this employee's current projects"), not a per-project query. `findAllForProject` (EPIC-0004's org-wide report pattern the user referenced) answers a different question ("who is currently on this project") and was designed for the org-wide/per-project report's project-centric iteration, not an employee-list's employee-centric iteration. No new repository method is needed: `findAllForEmployee` already returns `projectName` and a repository-computed `temporalStatus` per row, so the entire computation is a filter + map + dedupe in Domain Logic over data already being fetched by an existing call.

**Alternatives considered**:
- *A new repository method, e.g., `findCurrentProjectNamesForEmployee(employeeId)`, filtering to current in SQL* — rejected: `temporalStatus` isn't a stored column either (it's computed per-row from `start_date`/`end_date` via `isInFuture`/`includesToday`, the same `date-utils.ts` primitives used everywhere else), so a SQL-level `WHERE temporalStatus = 'current'` isn't directly expressible without duplicating that date logic into a raw SQL predicate — the same duplication problem the `minAvailability`/`sort=utilization` decision above already rejected for utilization. Filtering the existing `AssignmentRecord[]` in Domain Logic (where `temporalStatus` is already a materialized field on each returned record) avoids this entirely.
- *`findAllForProject`, iterating per-project instead of per-employee* — rejected per Rationale above: wrong access pattern for a per-employee list endpoint, and would require an additional cross-referencing step (project → its currently-assigned employees → back to each employee's list entry) that `findAllForEmployee`'s direct per-employee call avoids.

**Accepted trade-off, stated explicitly, not incidental**: this is a genuine N+1 query pattern — one `findAllForEmployee` call (a query joining `assignments`/`employees`/`projects`/`project_roles`) per employee in the list, on top of the one call per employee `EmployeeService.listEmployees` already makes for utilization. At demo scale (tens of employees, per the constitution's Principle V rationale and every prior epic's stated scale assumption), this means tens of extra small queries per `GET /employees` request against a local SQLite file with no network round-trip — the same cost class `bench.service.ts` already accepts (one `findAllForEmployee` call per employee, every bench request) and `reports.service.ts`'s org-wide report already accepts (one `getCurrentUtilization`, i.e. one more `findAllForEmployee`-derived call, per employee, every report request). This is not a new performance pattern introduced by this epic; it is the same accepted pattern this codebase already uses in two other places for the same reason: at this scale, a batched/joined single-query alternative would add real complexity (a new cross-employee aggregation query, duplicating logic `findAllForEmployee` already correctly encapsulates) to avoid a cost that doesn't actually matter yet. If this system ever moved beyond demo scale, batching this into a single query (or a `findCurrentProjectNamesForAllEmployees()`-style bulk method) would be the correct fix — but introducing that complexity now, for a cost class this codebase has already twice decided is acceptable, would be solving a problem that doesn't exist at the stated scale.

## Decision: `EmployeeService` gains a constructor dependency on `AssignmentService`; `listEmployees` returns utilization-annotated records, so the route stops recomputing it separately

**Question this decision resolves** (not explicitly asked by the plan input, but required to actually implement its "compute in Domain Logic" decision without introducing a new duplication): `EmployeeService` currently has no dependency on `AssignmentService` — `listEmployees` is a one-line passthrough to `EmployeeRepository.findAll`. The route (`employees.routes.ts`'s `GET /` handler) currently computes `currentUtilizationPercent` itself, per employee, via its own `assignmentService.getCurrentUtilization` call, *after* calling `service.listEmployees(filters)`. If `EmployeeService.listEmployees` now also needs utilization per employee internally (to filter by `minAvailability` and sort by `utilization`, per the decision above), computing it there *and* leaving the route's existing separate computation in place would mean calling `getCurrentUtilization` twice per employee for the same value — the exact duplication this project's centralization principle exists to prevent.

**Decision**: `EmployeeService` takes `AssignmentService` as a new constructor dependency (no cycle: `AssignmentService` depends only on repositories, not on `EmployeeService`, confirmed by inspection). `listEmployees(filters)` now returns `Array<EmployeeRecord & { currentUtilizationPercent: number }>` — utilization-annotated employee records, already filtered by `minAvailability` and sorted by `sort=utilization` when requested. The route's `GET /` handler is simplified to use that returned `currentUtilizationPercent` directly when building each `EmployeeSummary`, instead of making its own separate `getCurrentUtilization` call per employee.

**Rationale**: This is the only way to honor both "one shared utilization computation, never duplicated" (Principle II/NFR-0009) and "filtering/sorting by utilization requires the value to already be computed" (the structural constraint above) at the same time. It also simplifies the route, which no longer needs its own `Promise.all`-based utilization-fetching loop for the list endpoint — that responsibility moves fully into `EmployeeService`, consistent with Domain Logic owning this computation rather than splitting it across two layers.

**Alternatives considered**: Leaving the route's existing utilization computation in place and adding a second, separate one inside `EmployeeService` purely for filtering/sorting — rejected as exactly the duplication described above, with no offsetting benefit (both calls would produce the identical number for the identical employee on the identical request).

## Decision: `minAvailability` uses explicit `ValidationError` → 400 rejection (reusing the existing error type, not a new one); `sort`'s pre-existing leniency is untouched and is a separate matter

**Question raised explicitly**: state `minAvailability`'s exact validation behavior — what happens for a negative value, a non-numeric value, and a value over 100 — and decide deliberately whether it should follow this project's stricter numeric-input pattern (explicit 400) or a lenient one, rather than leaning on an analogy to `sort`'s existing behavior.

**Correction from an earlier draft of this document**: an earlier version of this decision reasoned by analogy to `sort`'s existing lenient fallback (unrecognized `sort` values silently default to `"name"`, confirmed in `employee.repository.ts`) and concluded `minAvailability` should behave the same way. That analogy doesn't hold up: `sort`'s leniency is *pre-existing* route behavior this epic doesn't touch (it predates this epic and was never flagged as a gap), not a considered precedent for how a *new* numeric input should behave. The actual relevant precedent in this codebase is every other numeric business input, and that precedent is unanimous in the opposite direction:
- `capacityPercent` (`assignment.service.ts:41-46`): `input.capacityPercent <= 0 || input.capacityPercent > 100 || !Number.isInteger(input.capacityPercent)` → `throw new ValidationError("capacityPercent must be an integer greater than 0 and up to 100.")`.
- Bench `window` (`bench.service.ts:47-48`): any value outside the fixed enum → `throw new ValidationError('window must be one of "now", "30d", "60d", "90d".')`.

Both existing numeric/enum business inputs are validated with an explicit, immediate 400 rejection — neither silently ignores nor silently coerces a bad value. There is no deliberate reason for `minAvailability` to be the first exception to that pattern; silent leniency here would just be an oversight repeating the same mistake the `sort` analogy already was.

**Decision (revised)**: `minAvailability`, when provided, MUST be an integer between 0 and 100 inclusive. Exact behavior:
- **Absent** (not provided in the query string): no filter is applied — unchanged, existing default behavior for every optional filter on this endpoint.
- **Negative** (e.g., `minAvailability=-5`): rejected — `400 VALIDATION_ERROR`.
- **Non-numeric** (e.g., `minAvailability=abc`): rejected — `400 VALIDATION_ERROR`.
- **Non-integer** (e.g., `minAvailability=50.5`): rejected — `400 VALIDATION_ERROR`, for the same reason `capacityPercent` requires an integer (percentages in this system are always whole numbers).
- **Over 100** (e.g., `minAvailability=150`): rejected — `400 VALIDATION_ERROR`.
- **Exactly 0**: valid, not an error — matches spec.md's edge case ("every employee matches, including a fully-booked one") and is meaningfully different from "absent" only in that it's an explicit, deliberate filter value, not a signal to skip filtering.
- **Exactly 100**: valid, not an error — matches only employees with zero current assignments.

Message text follows the existing `capacityPercent` convention: `"minAvailability must be an integer between 0 and 100."`, thrown as the existing `ValidationError` (no new error type — Principle IV's "no new error type" conclusion in plan.md's Constitution Check remains correct; only the specific behavior described here changes, not that conclusion).

`sort`'s existing lenient fallback for unrecognized values (including anything that isn't `name`/`employmentStartDate`/the new `utilization`) is explicitly left unchanged by this epic — it was not part of the confirmed gap list, and changing it would be unrelated scope creep into a pattern that predates and is independent of this epic's three confirmed gaps.

**Test cases added to the integration backfill** (per this decision): `minAvailability=-5`, `minAvailability=abc`, `minAvailability=150` — each asserted as `400` with `error_code: "VALIDATION_ERROR"`.

## Decision: test coverage backfill — integration tests only, added to existing files

**Decision**: FR-0025/FR-0026's existing-but-untested parameters (`skill`, `proficiency`, `seniority`, `name`/`employmentStartDate` sorts on `GET /employees`; `status`, `requiredRole`, `startDateFrom`/`startDateTo`, `name`/`startDate`/`endDate` sorts on `GET /projects`) are backfilled as integration test additions to the existing `tests/integration/employees.api.test.ts` and `tests/integration/projects.api.test.ts` files (both already exist, confirmed via direct inspection — zero existing test cases exercise any query-string parameter in either file today), not new files and not unit tests.

**Rationale**: Per the user's explicit instruction — the underlying filter/sort logic already works correctly (confirmed by the prior codebase audit), so unit tests would only re-assert what a Kysely query builder already does; integration tests against real SQLite are what actually prove the end-to-end wiring (query param → repository `WHERE`/`ORDER BY` → real rows), which is the thing that was actually unverified.
